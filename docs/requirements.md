# Требования к моделям, железу и зависимостям

Дата: 22 октября 2026. Это проект требований. Пока нет реализации и нагрузочных измерений, цифры памяти/диска ниже — целевые конфигурации и бюджеты тестирования, не доказанные минимумы или обещания скорости. Версии конкретных моделей и библиотек фиксируются в release после проверок.

## 1. Режимы

| Режим | Где вычисляется визуальная оценка | Что требуется пользователю | Статус |
|---|---|---|---|
| `host-vision` | В модели выбранного Codex/Claude-хоста | Работающий хост с просмотром изображений/инструментами, доступ к модели, сеть; локальный runtime | Основной путь первой версии |
| `local-signals` | Только локальные численные признаки; художественного vision нет | CPU, runtime, подходящий декодер | Подготовка/технический partial report; не полноценная замена художественного отбора |
| `api` | Отдельный выбранный vision API | Всё для локальной подготовки + credentials, квота и бюджет API | Расширение для массового запуска без участия пользователя |
| `local-vision` | Локальная мультимодальная модель | Отдельные веса, совместимый inference runtime и измеренный запас RAM/VRAM | Экспериментальное расширение после MVP |

В основном дизайне `local` — общий режим без сетевой модели; capabilities различают `local-signals` и `local-vision`. Запуск программы на ноутбуке не делает `host-vision` офлайн. Локальность Python-обработки и местоположение модели — разные настройки.

При host-vision проект использует выбранный хост, без отдельного обязательного API-клиента внутри Python. Способ авторизации/лимиты зависят от установки хоста; установка скилла не предоставляет доступ к модели. API-вариант имеет собственные credentials/тарификацию: нельзя считать доступ из чата API-квотой.

## 2. Требования к модели и хосту

Модель для полного отбора должна:

- Принимать реальные изображения, а не только описание, EXIF или текстовый OCR. Text-only модель годится для оркестрации при отдельном vision backend, но не может сама оценить фотографии.
- Сравнивать несколько вариантов с устойчивой привязкой к item/asset IDs; стартовые batches — 2–6 отдельных изображений, с уменьшением под возможности провайдера. Contact sheet — обзор, не доказательство фокуса.
- Работать с общим видом и отдельными кропами деталей, сохранять связь кропа с исходным кадром.
- Следовать жанровой рубрике, различать технический дефект и возможное художественное намерение, возвращать uncertainty/abstain при недостаточных данных.
- Возвращать структурированный результат с допустимыми IDs и критериями. Native structured outputs желательны, но не обязательны: schema validation и ограниченные повторы выполняет runtime.

Хост должен уметь обнаружить скиллы, прочитать файлы/references, запустить CLI, передать модели изображения и получить результат. Tool use обязателен для агента-оркестратора; отдельный vision API может быть простым image-in/JSON-out компонентом. Для LightCraft требуется доступ к его интеграции именно в выбранном хосте.

Не задавать универсальный минимум вроде «128k context». Требование — вместить ограниченный batch с рубрикой и результатом; остаток состояния лежит на диске. Поддержку устанавливать end-to-end probe связки **host + model + image path/tool**, а не только по рекламной спецификации модели. Лимиты API не переносить автоматически на Codex/Claude Code.

OpenAI и Anthropic документируют resize изображений и ошибки визуального анализа. Они принимают распространённые растровые форматы; исходный RAW сначала декодируется в превью/кроп. EXIF извлекается отдельно и передаётся как структурированные данные при необходимости. [OpenAI vision](https://developers.openai.com/api/docs/guides/images-vision), [Claude vision](https://platform.claude.com/docs/en/build-with-claude/vision).

**Выбор модели:** первую reference-реализацию проверять на сильной мультимодальной модели, доступной в каждом целевом хосте. Название модели не является контрактом качества. После baseline более дешёвый вариант допускается на отдельный этап только при сохранении quality gates. Финальные спорные кадры и жанровый топ можно отдавать более сильной модели; такая маршрутизация добавляется после измерения её пользы.

В `model-profile.json` фиксировать provider, точный model ID/revision при наличии, host version, image settings, batch limits, prompt/profile versions, schema mode и измеренные quality/latency/cost. При плавающем model alias записывать доступную версию/дату и повторять dev-regression после смены. Модель имеет статус supported только после наших фото-evals; smoke установки проверяет доступность, а не художественное качество.

## 3. Железо для первой версии

Первая целевая платформа — macOS на Apple Silicon; поддержка конкретных версий macOS определяется пересечением требований Python/wheels, хоста и выбранного редактора. Intel Mac/Windows/Linux не объявляются поддержанными до CI и интеграционных проверок; переносимость Python не доказывает поддержку Adobe или MCP на каждой ОС.

| Профиль для проверки | RAM компьютера | CPU и GPU | Применение |
|---|---|---|---|
| Ограниченная конфигурация | 8 ГБ | Современный 64-битный CPU, 1 RAW-worker; GPU ядру не нужен | Небольшие порции, закрытый тяжёлый редактор; поддержка пока не подтверждена |
| Основной целевой | 16 ГБ | Многоядерный CPU, старт с 1–2 RAW-workers; без отдельной GPU для culling | Отбор через host-vision, потоковая обработка съёмки |
| Комфортный целевой | 32 ГБ | Многоядерный CPU, SSD; concurrency по свободной памяти | Несколько тысяч RAW, параллельно открыт редактор |

Количество фото влияет прежде всего на время и диск; всё изображение каждой фотографии не держится в памяти одновременно. Стартовый soft budget Python-процесса на 16 ГБ машине — 3 ГБ RSS без памяти хоста/редактора/локальной модели. Планировщик ограничивает workers по наблюдаемой памяти и размерам кадров; при превышении снижает concurrency или выдаёт понятный partial result. Это цель реализации, проверяемая benchmark-ом, а не гарантия для любого RAW.

Пример расчёта: 45 MP RGB-изображение занимает около 270 MB при 16 bit/channel или 540 MB в float32, ещё до RAW-буфера и временных копий. Поэтому даже две операции полноразмерного рендера могут быть заметно тяжелее тысяч уже сжатых thumbnails.

Требования редактора действуют отдельно: отсутствие требования GPU у нашего CPU-ядра не отменяет GPU-требований Lightroom/Photoshop. Adobe для Lightroom Classic указывает 8 ГБ RAM минимум и 16 ГБ+ рекомендуемо, с дополнительными условиями GPU для ускорения и AI-функций. Наши 32 ГБ — инженерный ориентир для совместной работы приложений, а не заявленный минимум Adobe. [Lightroom Classic requirements](https://helpx.adobe.com/lightroom-classic/desktop/introduction-to-lightroom-classic/system-requirements.html).

## 4. Диск, сеть и стоимость

Использовать SSD для кэша и рабочих артефактов. Предварительный резерв: до 5 ГБ для базового runtime/подготовки установки и обновления плюс 10–20 ГБ рабочего места на сессию среднего размера; реальные размеры зависят от wheels, превью и политики кэша. Оригиналы, копии для экспорта, кэш редактора и локальные модельные веса считаются отдельно. Установщик показывает фактическую оценку выбранных компонентов вместо универсальной цифры.

Формула оценки кэша: `N × средний размер превью + thumbnails/contact sheets + выбранные кропы + журналы + временные файлы`. Если превью имеет 0.3–1.5 MB, то 1000 превью займут примерно 0.3–1.5 GB, 5000 — 1.5–7.5 GB. Это арифметический пример, не гарантированная степень JPEG-сжатия. Постоянное хранение полноразмерных TIFF для всех кадров не входит в default.

Перед запуском оценивать место по небольшой выборке, задавать cache quota и контролировать свободное место при записи. Кэш пересоздаваемых превью можно очищать; originals, decisions, overrides и receipts — нет. При экспорте копий отдельно резервируется их объём.

Host/API vision требует сети и допускает передачу соответствующих изображений провайдеру. JPEG/PNG-превью и кропы передаются по выбранному режиму, RAW-файл целиком обычно не нужен. Повторные сравнения и кропы тоже расходуют лимиты; стоимость считать по всей сессии, не по одному вызову. При исчерпании лимитов — checkpoint/partial, а не незаметный переход на другой облачный backend.

## 5. Зависимости production

| Компонент | Для чего | Установка |
|---|---|---|
| Python 3.12, зафиксированный patch release | Общий runtime | Управляется установщиком через uv; не требует ручной настройки virtualenv |
| uv | Python/окружение/locked зависимости | Bootstrap prerequisite; мастер проверяет или объясняет установку |
| Pillow, NumPy | Превью, цвет/ориентация, массивы и численные признаки | Базовый пакет |
| Pydantic | Контракты, валидация результатов | Базовый пакет |
| sqlite3, json, pathlib, argparse | Состояние, обмен, CLI | Стандартная библиотека Python, не отдельный сервер БД |
| ExifTool | Полное чтение метаданных и поддержанный XMP-обмен | Внешняя версионированная зависимость MVP; установка/проверка под ОС |
| rawpy/LibRaw | Независимое полноразмерное декодирование RAW и кропы | RAW extra; обязателен для RAW-сценария без проверенного рендера редактора |
| Интеграция выбранного редактора | Применение и чтение разметки | Только для выбранных host/editor комбинаций |

rawpy выпускает бинарные wheels для нескольких 64-битных платформ и использует LibRaw. Для релиза проверять наличие wheel именно для выбранных Python/OS/architecture и поддержку пользовательских камер. Не заставлять обычного пользователя собирать C/C++ зависимость; неподдержанную комбинацию объяснить или предоставить проверенный альтернативный рендер. [rawpy installation](https://github.com/letmaik/rawpy#installation).

ExifTool — не обычный Python-wheel; Unix-вариант и платформенные пакеты имеют собственные runtime requirements. Сборка должна зафиксировать способ доставки и проверить реальный запуск на чистой машине. Наличие утилиты в PATH на компьютере разработчика не считается готовым installer-ом.

Модельные SDK, Torch/CUDA, OpenCV, embedding/IQA-веса не входят в обязательный MVP. Добавлять их отдельными extras после доказанного выигрыша. Node.js и Docker не являются зависимостями нашего runtime; требования установленного агентского хоста учитываются отдельно. Для статического отчёта нужен обычный браузер. Следующая HTML-review итерация поставляет готовые HTML/CSS/JS, без Node-сборки на компьютере фотографа.

Bootstrap должен работать без заранее настроенного Python 3.12: платформенный launcher использует uv-managed Python для запуска `install.py`. Конкретные команды bootstrap проверяются при реализации; инструкция не должна начинаться с Python-скрипта, если интерпретатор ещё не предоставлен. Runtime и dev groups изолированы, версии фиксируются lockfile. [uv environments](https://docs.astral.sh/uv/concepts/projects/sync/).

## 6. Полностью локальная модель — отдельный профиль

Обязательна мультимодальная модель с image encoder и проверенным качеством на наших данных. Поддержка текстовой LLM в inference runtime не означает поддержку её vision-варианта. Проверять также multi-image input, preprocessing, quantization, ограничения лицензии и фактическую память с нужным batch.

Без выбора весов нельзя честно назначить универсальный минимум VRAM. Нижняя оценка только весов: `число параметров × битность / 8`; например, 8B при 4 bit — около 4 GB до дополнительных тензоров, vision encoder, KV-cache, activations и runtime overhead. Разрешение, число изображений и длина контекста меняют потребление.

Для будущих опытов с небольшой квантизованной VLM можно планировать стенд 32 ГБ unified memory либо 32 ГБ системной RAM + 12–16 ГБ VRAM. Это исследовательский бюджет, не обещание запуска любой модели и не рекомендация покупать железо сейчас. После выбора backend и модели зафиксировать measured peak RAM/VRAM, скорость и quality gates; до этого local-vision остаётся experimental. CPU-only inference не запрещать, но скорость быстрого culling на нём не обещать.

## 7. Dev и evals

Dev-only: pytest и прочие test/build инструменты, harness, graders, benchmark fixtures, browser test tooling второй итерации. Vision-evals требуют доступа к проверяемым хостам/API; сравнение редакторов — тестовых каталогов и соответствующих установленных программ.

Вычислительная конфигурация может совпадать с пользовательской; существенно растут объём данных, время, число повторов и расходы модели. Прогоны можно выполнять последовательно, отдельная GPU для host-vision evals не требуется. CI без Adobe/LightCraft выполняет контрактные проверки, но не считается подтверждением реального editor round-trip.

## 8. Что проверяет установщик и что подтверждает релиз

Установщик/doctor: OS/architecture, Python/uv, доступное место, зависимости/RAW-декодер, host vision capability, модельный режим, редактор/backend, доступные поля метаданных. Минимальный image smoke использует тестовую картинку без пользовательских данных; сетевой smoke выполняется в явно выбранном сетевом режиме и не выдаётся за фото-eval. Результат по capability: ready / degraded / unavailable с причиной.

Dev-release matrix: 8/16/32 ГБ, 1/2 workers, 24/45/60+ MP, 100/1000/5000 файлов, cold/warm cache, одновременный редактор, низкое место, отсутствие сети/vision, поддержанные камеры. Измерять peak RSS, disk, latency, visual calls и качество, не только время подготовки. Реальные минимумы публикуются после этой проверки; будущие модели допускаются отдельно через quality evals.
