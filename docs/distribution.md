# Dev, пользовательская поставка и установщик

Дополнение к дизайну от 22 октября 2026. Требования пользователя: разделить разработку и установку, не включать evals в обычную пользовательскую поставку, дать выбор программы обработки и использовать её интеграцию для записи метаданных. Основной dev-репозиторий уже создан пользователем: [sendelufa/silverloupe](https://github.com/sendelufa/silverloupe). Название проекта — Silverloupe. Отдельный install-репозиторий пока описан как роль поставки, его адрес не задан.

## 1. Два представления проекта

| Представление | Состав | Кто использует |
|---|---|---|
| Dev-репозиторий | Исходники runtime и шести рабочих скиллов; dev-only eval-скилл; тесты; eval harness; рубрики; build/release tooling; документация разработки | Разработчик и CI |
| Install-репозиторий и release-архив | Собранные шесть рабочих скиллов; runtime; установщик; нужные profiles/templates/adapters; production lock; manifest/checksums; лицензии и краткая инструкция пользователя | Фотограф |

Предлагаемая организация: один источник истины в dev-репозитории, install-репозиторий генерируется CI из выбранного release tag. Вручную изменения в install-репозитории не поддерживаются; исправление делается в dev и проходит новую сборку. Тот же артефакт публикуется как архив для установки без Git. Адрес install-репозитория выбирается перед публикацией; новый удалённый репозиторий автоматически не создаётся.

Production не содержит `silverloupe-eval`, `evals/`, `tests/`, gold labels, тестовые фотографии, benchmark reports, traces, внутренние планы и зависимости pytest/eval runners. Исключение должно выполняться физически при сборке, а не только скрывать команду в меню. Обычный пользователь не клонирует dev-репозиторий для установки и не запускает evals.

Runtime validation остаётся: проверка входных данных, допустимых путей/ID, конфликтов метаданных, capabilities и результата записи — часть работы продукта. `doctor` диагностирует установку без тестовых съёмок и не является исследовательским eval.

## 2. Состав репозиториев

```text
silverloupe/                       # dev: sendelufa/silverloupe
  skills/                          # только 6 production-скиллов
  dev/skills/silverloupe-eval/
  src/silverloupe/                # runtime + installer; без импортов evals
  resources/                       # единственные исходники ресурсов
  evals/                           # runner, graders, TrialResult
  tests/
  tools/build_collection.py
  packaging/production-manifest.json
  pyproject.toml                    # dev/eval группы изолированы
  uv.lock
  docs/

install-repo/                      # генерируется, не отдельная реализация
  install.py                       # bootstrap CLI; установка без dev-checkout
  manifest.json
  checksums.json
  skills/                          # 6 скиллов + их runtime references
  runtime/                         # production package и locked environment spec
  adapters/                        # поддержанные варианты редакторов
  templates/                       # только выпущенные шаблоны
  USER_GUIDE.md
  LICENSES/
```

Сборка использует allowlist; CI распаковывает итоговый архив и проверяет отсутствие dev-only файлов/зависимостей и незамкнутых ссылок. Обязательно установить именно release-артефакт в чистую среду без исходного dev-репозитория. Evals в CI запускают эту же сборку как испытуемый продукт, а не расширенный dev runtime.

Manifest: release/core/skills/schema/template versions, source commit/tag, поддержанные platform/host/editor combinations, artifacts и hashes, runtime dependencies, ownership list для удаления. Выход сборки воспроизводим для одного исходника/lock/платформы; release pipeline не перезаписывает артефакт уже опубликованной версии. Checksums проверяют целостность; подлинность источника обеспечивается отдельно доверенным release-каналом и в дальнейшем проверяемой подписью, а не самим хешем.

## 3. Установщик — первая пользовательская итерация

[Требования к моделям и окружению](requirements.md) задают профили host-vision/local/API, состав зависимостей и проверку ресурсов. Bootstrap предоставляет uv-managed Python через платформенный launcher; не требует заранее настроенного Python 3.12 для запуска самого `install.py`.

Пользовательский сценарий:

1. Запустить установщик из release-поставки; выбрать Codex, Claude Code или оба, область установки и каталог runtime.
2. Выбрать Lightroom Classic, Lightroom cloud, Photoshop через Bridge/Camera Raw или LightCraft. Допускается несколько редакторов; один назначается основным.
3. Установщик проверяет поддержанную версию редактора, доступность интеграции и возможности записи: rating/keywords/label/flag. Наличие установленного приложения не означает наличие рабочего API. Проверки установки не меняют пользовательские фото.
4. Установить runtime через uv с production-зависимостями, зарегистрировать рабочие скиллы и выбранные адаптеры. Не устанавливать dev/eval зависимости, все модели и все интеграции «на всякий случай».
5. Сохранить настройки и показать результат: активный редактор, способ записи, поддержанные поля, ограничения и пример первого запуска. Если запись недоступна, показать `report-only` и точную недостающую интеграцию; не сообщать, что metadata backend готов.

Предлагаемый интерфейс будущих команд: `install.py --host codex --editor lightcraft`, `silverloupe configure --editor lightroom-classic`, `silverloupe doctor`, `silverloupe update --version ...`, `silverloupe uninstall`. Это требования к интерфейсу, а не уже работающие команды. Для запуска без параметров предусмотрен интерактивный мастер; для автоматизации — эквивалентные параметры.

`InstallConfig`: config_version, hosts, scope, install_root, enabled_editors, default_editor, integration_mode_by_editor, metadata_mapping_by_editor, runtime_version, model_mode, model_profile, cache_quota, worker_limit. В `SessionConfig` сохраняется snapshot выбранного профиля и capability versions: смена основного редактора не меняет уже построенный delivery-plan.

Установщик не предполагает, что MCP в Codex автоматически доступен Claude. Настройка каждого хоста проверяется отдельно; если нужно подключение/вход в приложение, мастер объясняет конкретный шаг. Без нужной интеграции остаётся отчёт, либо явно выбранный совместимый файловый режим.

## 4. Выбор программы определяет запись

Canonical decisions преобразуются в `MetadataPatch`, затем выбранный `MetadataBackend` создаёт/обновляет разметку и читает её обратно. Интерфейс backend: `capabilities()`, `plan(...)`, `apply(...)`, `readback(...)`; у каждого действия есть target identity, before/after и receipt. Смена backend требует перестроения плана.

| Редактор | Маршрут записи | Условие готовности |
|---|---|---|
| LightCraft | Нативные команды приложения для рейтинга, флага, меток/других доступных полей | Подключённый MCP на выбранном хосте и проверенный readback |
| Lightroom Classic | Адаптер приложения, если доступен и проверен; иначе явно выбранный XMP-обмен для поддержанных форматов | Нативную интеграцию не обещать до probe; для XMP нужен подтверждённый цикл чтения редактором |
| Photoshop | Адаптер Bridge/Camera Raw для передачи выбранных файлов и разметки; согласованный XMP-обмен как поддержанный вариант | Отдельно проверенные версии и поля; Photoshop не трактуется как каталог с универсальным API флагов |
| Lightroom cloud | Отдельная интеграция под подтверждённые возможности версии | До проверки — not supported/report-only, без подмены Classic-поведением |

Предпочитать запись через выбранную программу, когда backend реально доступен. Если выбран `native`, отсутствие capability не разрешает молча перейти на прямую правку XMP. Файловый режим показывается и выбирается явно при настройке; потом используется без повторного вопроса в каждой сессии. Не писать в XMP и каталог одновременно двумя независимыми writers. Поля, которые backend не поддерживает, остаются в отчёте с понятным статусом.

Детали Adobe SDK/API и автоматизация чтения метаданных — часть compatibility probes задач 7 и 9 плана. Пока они не проверены, поставка честно объявляет конкретный поддержанный маршрут, например XMP exchange, а не «полная нативная интеграция». Правила конфликтов, принятия reject, сохранности develop и rollback остаются общими для всех backends.

### 4.1 Повторное применение изменённого отбора

Receipt хранит ownership/provenance по каждому записанному полю: target identity, исходное значение/отсутствие поля до первой записи коллекцией, последнее собственное значение, session/revision и operation_id. Новый delivery-plan сравнивает желаемую разметку и предыдущий receipt с текущим readback. Если значение всё ещё совпадает с последним собственным postimage, можно обновить его (например, 5★ → 4★ при исключении только из top) или восстановить исходное значение при снятии всей собственной разметки. Если текущее значение отличается — conflict, ручная правка сохраняется.

Без receipt/provenance существующее значение считается пользовательским, даже если похоже на нашу шкалу. Для keywords ownership ведётся по добавленным элементам, а не всему списку; удаляются только наши элементы. Undo/replace не вызывают скрытую запись редактору: новые значения применяются отдельным delivery-plan. Rollback и повторный apply используют ту же проверку postimage. Неподдерживаемое backend-ом снятие поля отражается как skipped, а не успешная синхронизация.

## 5. Обновление, отказ и удаление

Установка идемпотентна, повторный запуск не создаёт дубли скиллов. Обновление готовит новую версию отдельно, проверяет зависимости/manifest и переключает активную версию после успешной подготовки. Ошибка подготовки оставляет предыдущую рабочую установку. Миграции конфигурации имеют резервную копию и явную проверку совместимости незавершённых сессий.

Удаление затрагивает только принадлежащие установке файлы/регистрации по ownership manifest. Фотографии, результаты сессий, правки пользователя и чужие скиллы сохраняются. Сеть требуется для получения отсутствующих runtime-зависимостей; офлайн-установка возможна из заранее полного пакета с локальными зависимостями. Установщик сообщает, что именно отсутствует, а не запускает скрытый сетевой bootstrap.

## 6. Приёмка поставки

Проверить чистую установку обоих хостов, выбор/смену редактора, отсутствие интеграции, пути с пробелами/Unicode, повторную установку, обрыв обновления, rollback, отсутствие dev-only материалов и удаление только owned files. На production-окружении отбор работает без pytest и `evals`; в списке скиллов отсутствует `silverloupe-eval`. Автоматические release tests выполняются разработчиком до публикации, не на устройстве фотографа.
