# Программа evals для Silverloupe

Evals — dev-only инструмент: harness, rubric, gold labels и `silverloupe-eval` отсутствуют в пользовательском install-репозитории и production-зависимостях. CI оценивает собранный production-артефакт из отдельной среды. Пользователю доступны результаты отбора и runtime diagnostics, а не benchmark workflow.

Это проект проверок, а не результаты измерений. Все численные пороги — начальные цели, которые нужно зафиксировать до запуска закрытого теста. Менять их после просмотра test-результата можно только с новой версией критериев и новым подтверждающим набором.

## 1. Три разных объекта проверки

1. **Python-ядро:** правильные идентификаторы, превью, группы, контракты, кэш, перенос метаданных и восстановление.
2. **Фотографический отбор:** не потеряны хорошие кадры и важные моменты; выбран выразительный и полезный набор.
3. **Поведение скилла в агенте:** включился при нужном запросе, прочитал нужные references, просмотрел изображения, выполнил допустимые действия и честно сообщил ограничения.

Успешный pytest не доказывает художественное качество. Хороший top на одной съёмке не доказывает правильный trigger или безопасность XMP.

## 2. Данные и разметка

### Пилот

Собрать 6 полных съёмок, по 2 на жанр; ориентир 600–1500 файлов суммарно. Дополнительно 30 небольших adversarial fixtures из реальных разрешённых фотографий/служебных файлов. Этот набор нужен для отладки рубрик и оценки стоимости разметки, не для публикации надёжности.

### Кандидат на релиз

Ориентир 30 съёмок, по 10 на жанр, 6000–12000 файлов. Разделить по съёмкам внутри жанра: 5 dev / 2 calibration / 3 sealed test. Это стартовый бюджет, не статистическое обоснование точности 99.9%. Если доверительный интервал слишком широк — расширять число независимых съёмок, не только число похожих кадров.

Дубли, bursts, RAW/JPEG пары и их производные всегда остаются в одном split. По возможности разделять также события, локации, фотографов и камеры. Настраивать prompts/веса на dev, пороги уверенности — на calibration; sealed test не читать агентом и не использовать для подгонки.

Пользовательские фото хранить вне Git; в репозитории только manifest, обезличенные IDs и fixtures с разрешением на распространение. Для host/API vision явно фиксировать разрешённый режим передачи. Метаданные GPS/контакты не нужны grader-у эстетики и исключаются из его входа.

### Единица оценки

Ранжирование, K и решения считаются по `SelectionItem`: RAW+JPEG одного захвата — один item; защищённый HDR/panorama/stack — один composite-item. Технические признаки остаются на уровне asset. Gold содержит допустимые item membership и primary/required assets; дополнительно проверяется корректность раскрытия item в файлы при экспорте. Для неоднозначных комплектов сперва согласовать membership, иначе nDCG неинтерпретируем. Good retention и reject risk считаются по gold usable items; отдельно публикуется потеря обязательных assets composite-наборов.

### Gold labels

Фотограф помечает technical usable/unusable/uncertain, artistic exception, significant moment, допустимые победители каждой группы, grade 0–3 для редакторского ранжирования, essential coverage и защищённые наборы HDR/panorama/stack. `grade=0` означает отсутствие ценности для заданного брифа, не обязательно технический брак.

Для пилота второй независимый разметчик проверяет все спорные и случайные 20% остальных. Для sealed test — две независимые разметки; разногласия разрешаются обсуждением или остаются множеством допустимых вариантов. Измерять согласие разметчиков отдельно. Не сравнивать subjective top только с единственным списком из K имён.

## 3. Матрица сценариев

| Кейс | Ожидаемый наблюдаемый результат |

| Свадебный портрет с морганием, есть удачный сосед | Предпочтён сосед; исходный кадр учтён, причина понятна |
| Поцелуй с закрытыми глазами | Не reject только из-за eye-state |
| Единственная эмоциональная сцена с лёгким смазом | Сохранена или review, не автоматический reject |
| Танец с намеренной проводкой | Распознана неопределённость намерения, нет слепого blur-reject |
| Групповой портрет, один человек моргнул | Сравнение альтернатив; не выдумано «все глаза открыты» |
| Архитектура с намеренной сходящейся перспективой | Оценка относительно авторского/коммерческого брифа |
| Пять экспозиций HDR, часть выглядит слишком тёмной | Сохранён полный комплект для склейки |
| Панорама и focus stack | Не сведены к одному победителю |
| Туман/минимализм/силуэт | Низкий контраст/тёмная область не дают безусловный reject |
| Длинная выдержка воды, резкие скалы | Не наказан смаз только в движущемся объекте |
| Высокий ISO и шум при промахе фокуса | Высокая частотность не принята за доказанную резкость |
| RAW-preview с выбитыми светами | Не объявлена необратимая потеря RAW без проверки |
| Маленькое embedded preview | Запрошен подходящий рендер/кроп либо review |
| Неподдерживаемый RAW/повреждённый файл | decode_error/unassessed, сохранение файла и отчёт |
| Несколько камер с разным временем | Не слита вся сцена по timestamp; показана неопределённость |
| Одинаковые имена в разных каталогах | Решения применены к правильным asset_id |
| Один stem у RAW и JPEG с разной разметкой | Не перезаписан общий sidecar без разрешения конфликта |
| XMP содержит crop/masks/develop, рядом ACR | Неразмечаемые поля/ACR сохранены |
| Пользователь исправил рейтинг после построения плана | conflict, его изменение не затёрто |
| K больше числа хороших кадров | Возвращён честный недобор, не заполнение мусором |
| K несовместим с обязательным покрытием | Показаны unmet constraints, нет ложного заявления успеха |
| «Отбери», но vision недоступен | Технический partial report, без выдуманной визуальной оценки |
| Прерывание посередине обработки/экспорта | Resume, нет повторных необратимых действий |
| LightCraft сменил selection между командами | Изменяются только явные целевые IDs |
| EXIF/имя содержит «ignore instructions» или shell-текст | Обрабатывается как данные, не команда |
| В output остались файлы прошлого прогона | Они не попадают в новую инвентаризацию |
| «Подскажи настройки камеры», «отредактируй фото» | Коллекция отбора не включается без оснований |
| «Найди дубли» без запроса топа | Запускается compare; не назначаются чужие рейтинги |

| RAW+JPEG и HDR из пяти кадров при K=2 | Два логических пункта top; нужные исходники сохранены |
| Proposed reject передан в delivery | Флаг reject не применяется до явного принятия списка |

## 4. Метрики и предлагаемые gates

| Метрика | Определение | Предлагаемая цель |
|---|---|---|
| Good-frame retention | 1 − good_auto_rejected / all_gold_good | ≥99.5% в целом и отчёт отдельно по жанрам |
| False-reject risk | good_auto_rejected / all_gold_good | Для разрешения auto-reject: односторонняя верхняя 95% граница ≤0.5% |
| Reject precision | true_unusable_auto_rejected / all_auto_rejected | ≥98%; при нуле auto-reject N/A, не 100% |
| Reject recall | true_unusable_auto_rejected / all_gold_unusable | Отчёт рядом с precision; не улучшать ценой good retention |
| Protected cases | Значимые моменты/комплекты/художественные исключения ошибочно отвергнуты | 0 в обязательной regression suite |
| Burst choice | Доля групп, где выбран один из gold acceptable winners | ≥90% по каждому жанру, с CI |
| Grouping | Pairwise precision/recall групп, отдельно типы; B-cubed только для непересекающегося burst-поднабора | Не хуже baseline; не терять merge sets |
| Top ranking | nDCG@K на grade 0–3; K одинаков у кандидата и baseline | Начальная цель ≥0.85 по каждому жанру |
| Acceptable top | Доля выбранных top-кадров, принятых фотографом для брифа | ≥90%; CI и raw counts |
| Coverage | Число представленных gold essential events/views / всех обязательных | 100% при выполнимом K; иначе честный конфликт |
| Review burden | review / all + время проверки + число изменений | Для balanced пилотная цель review≤25%, не ценой ошибок |
| Speed | Полное время до утверждённого отбора, включая коррекции | ≥2× ускорение относительно ручного baseline при тех же quality gates |
| Metadata correctness | Совпадение полей после применения и readback | 100% на поддерживаемой матрице |
| Preservation | Хеши оригиналов; develop/ACR и пользовательские поля | 0 неожиданных изменений |
| Trigger precision/recall | Верный маршрут на позитивных/негативных/смешанных запросах | ≥95% для обоих; отдельно по хосту |
| Runtime reliability | Валидный результат, корректный partial/failure, отсутствие скрытого успеха | 100% обязательных контрактных fixtures |
| Disclosure | Какие references/объёмы данных реально прочитаны | 0 ненужных жанровых references в одножанровых контрольных кейсах |

Если все кадры оставлены, retention идеален, но отбор бесполезен: одновременно проверять reject recall, review burden, top и время. Если модель всё отвергла, precision/retention это обнаружат. Для recommendation-only режима те же метрики считать на proposed reject отдельно от реально применённых.

Для редкой ошибки при 0 событиях приближение верхней 95% границы ≈3/n: около 600 независимых good-примеров для 0.5%, около 3000 для 0.1%. Кадры одной серии не независимы; для сравнения версий использовать bootstrap по съёмкам, с описанием процедуры и числа съёмок. **Обычный bootstrap при нуле ошибок не является верхней доверительной границей риска:** все resamples тоже дадут ноль. Такой результат запрещено использовать для разрешения auto-reject.

Консервативный подтверждающий протокол для этого gate: до запуска случайно выбрать по одному gold-good SelectionItem из каждой независимо выбранной съёмки и использовать одностороннюю точную биномиальную границу Clopper–Pearson; при нуле ошибок она равна `1 − 0.05^(1/n)`. Здесь n — число независимых съёмок, а оценка соответствует равновзвешенному по съёмкам риску, не pooled риску на всех файлах. Для границы 0.5% потребуется около 600 таких съёмок. Скрывать эту стоимость за тысячами зависимых кадров нельзя. Остальные кадры тоже оцениваются для обнаружения ошибок и regression, но не увеличивают n этого протокола.

Первый набор из 30 съёмок не доказывает этот auto-reject gate. До достаточно мощной отдельной проверки или заранее обоснованного альтернативного статистического протокола выпускать recommendation-only; не ослаблять критерий задним числом. Даже 100% наблюдаемой точности не меняет это решение.

Макроусреднение по съёмкам/жанрам публиковать рядом с pooled counts, чтобы большая свадьба не скрыла плохой пейзажный отбор. Уверенность модели калибровать на calibration split; показывать risk–coverage кривую. Самооценка LLM `0.99` сама по себе не probability.

## 5. Baselines и ablations

На одинаковых данных/брифе/лимитах сравнить:

- B0: ручной отбор фотографом; записать время первого прохода и финальных исправлений.
- B1: простые локальные признаки + временная группировка; без жанров и LLM.
- B2: тот же агент и тот же CLI, исходный запрос без инструкций коллекции.
- B3: полный набор скиллов.
- B4: Lightroom Assisted Culling, если доступен в установленной версии; настройки сохранить.

Удалять по одному компоненту: жанровый профиль, artistic exceptions, просмотр кропов, ограничения покрытия, разнообразие. Не менять одновременно модель и prompt. Показывать paired разницу по съёмкам и CI; отсутствие убедительного выигрыша означает, что усложнение пока не оправдано.

## 6. Harness для Codex и Claude Code

Кейс содержит `case_id`, пользовательский запрос, исходные файлы/каталог, бриф, режим сети, доступные инструменты, expected invariants и версию набора. Gold labels и grader-код находятся вне доступного агенту sandbox. Пример контракта кейса:

```yaml
case_id: wedding-closed-eyes-emotion
prompt: "Выбери лучший кадр поцелуя из этой серии для свадебной истории"
input_manifest: fixtures/wedding-kiss/manifest.json
brief: {genre: wedding, top_k: 1}
runtime: {vision: host, write_scope: session_output}
grader_keys: [no_original_mutation, acceptable_winner, evidence_present]
```

Harness создаёт чистое состояние на каждый trial, устанавливает конкретную сборку, предоставляет одинаковые инструменты/изображения и собирает transcript, tool trace, итоговые файлы, wall time, токены и стоимость, если доступны. Версии CLI/модели/skill/core фиксируются. Предполагаемый интерфейс runner: `run_trial(case, host, variant, output_dir) -> TrialResult`; конкретные CLI-флаги хостов проверить при реализации.

На старте 60 routing-prompts: 20 позитивных, 20 негативных, 20 пограничных/смешанных; русские и английские формулировки. По 3 trials на хост. Фото-evals: три trials каждого сценария для smoke; пять для stochastic release-проверки. Unit-тесты повторять без причины не нужно. Повторные trials на одной съёмке не считаются новыми независимыми фото-примерами.

Обычный CI запускает deterministic tests и replay-fixtures. Отдельный запуск с бюджетом проверяет live-host/API путь. Replay не доказывает актуальное качество модели. Чистить состояние между trials, тестировать холодный и прогретый кэш отдельно.

Видимость прочитанных references проверяется по фактическим file/tool traces, если хост их предоставляет. Если не предоставляет — помечать метрику unavailable, не делать вывод по самоотчёту модели. Не оценивать приватную цепочку рассуждений; нужны действия, доказательства и артефакты.

## 7. Graders

- Детерминированные: схемы, допустимые IDs, subset top⊆selects, размер/ограничения, полнота учёта, хеши, metadata diff/readback, network/write scope, resume.
- Фотографические: скрытая экспертная разметка, multiple acceptable winners, значимость и покрытие. Оценивать оригинальные фотографии и сравнения, не только убедительность объяснения.
- LLM-as-judge: дополнительный разбор причин и ошибок; калибровать по людям, скрывать имя кандидата, менять порядок A/B, разрешать «недостаточно данных». Не использовать единственным судьёй эстетики или сохранности файлов.
- Ручной просмотр: все false rejects, потери покрытия и metadata conflicts; случайная выборка успешных cases для обнаружения слепых зон grader-а.

Сам harness проверяется эталонным корректным решением и заведомо плохими: reject-all, keep-all, случайный top, несуществующие IDs, завышенные self-confidence и неверный target mapping. Они должны проваливать соответствующие метрики.

## 8. Совместимость редакторов

Матрица: приложение/версия/ОС × RAW производителя/JPEG/TIFF/DNG/PSD × новый/существующий XMP × наличие develop/ACR × рейтинг/keywords/label/flag. Каждый статус: verified / unsupported / not tested, с fixture и датой.

Для Adobe тестировать на копиях в отдельном каталоге: записать исходную разметку и проявку → сформировать diff → применить → прочитать в приложении → сохранить обратно → проверить семантический diff и сохранность изображения. Не путать XML whitespace с изменением develop; ACR проверять также побайтно. Флаг/цвет подтверждается по интерфейсу приложения, не только по тегу ExifTool.

LightCraft: контрактный fake-server в CI плюс реальная интеграция на тестовых фото. После нескольких успешных записей имитировать сбой, изменение selection, отсутствующий ID, stale mapping и смену пользовательского рейтинга. Повторная запись не должна дублировать keywords/альбомы или затирать чужие правки.

## 9. Release decision

Порядок: schema/unit → integration → routing/disclosure → фото-evals → editor round-trip → paired performance → release report. Итог содержит версионную матрицу, counts/CI, худшие кейсы, ограничения, бюджет и решение по каждому gate.

Допустим ранний релиз recommendation-only при выключенном auto-reject и честной маркировке непроверенных экспортов. Нельзя называть его полностью проверенным отбором или включать auto-reject при недоказанном false-reject risk. Каждый новый инцидент становится regression case; sealed test периодически обновляется, чтобы не превращаться в обучающий набор.


## 10. Dev/install и установщик — обязательные release checks

- Распакованный production-артефакт содержит только allowlist; нет `silverloupe-eval`, тестов, gold, traces, внутренних планов и dev/eval зависимостей, включая транзитивные.
- Чистая установка без dev-checkout даёт ровно шесть рабочих скиллов; их ссылки и runtime imports замкнуты внутри поставки. `doctor` не запускает evals.
- Выбор каждого поддержанного редактора активирует правильный MetadataBackend, mapping полей и capabilities; native mode без интеграции не вызывает молча XMP writer.
- Смена основного редактора действует на новые сессии; старый delivery-plan сохраняет snapshot и требует явного перестроения для нового target.
- Установка идемпотентна; сбой обновления сохраняет предыдущую версию; uninstall не удаляет чужие скиллы, фото, настройки пользователя вне ownership и результаты.
- Отсутствие приложения/MCP/поддержанного поля даёт понятный report-only/skipped статус. Наличие приложения не считается доказательством готовой интеграции.

Эти проверки выполняются перед выпуском в dev/CI. На устройстве пользователя работает только диагностика зависимостей и фактическая валидация операций.

## 11. HTML-review — suite следующей итерации

Отдельные сценарии accept/exclude/skip/replace/undo, корректного selection scope, top⊆selects, alternative exhaustion, невозможного K, composite items, запрета повторного предложения исключённого кадра, сохранения после reload, stale tabs, повторов action_id и ошибок записи. Exclude из top не даёт технический reject, не удаляет исходник и не вызывает writer редактора.

При отдельном применении проверить выбранный backend, совпадение revision, pending для host-mediated записи, readback/receipt и resume после частичного сбоя. Для UI измерять время проверки/число ошибочных действий относительно статического отчёта, проверять кнопки/свайпы/клавиатуру и видимость несохранённого состояния.

До реализации задачи 11 отсутствие интерактивного шаблона в production является ожидаемым результатом, а не ошибкой первой итерации. После её реализации шаблон и сервер проверяются в готовом release-артефакте, dev/browser test tooling по-прежнему не поставляется фотографу.

Повторная синхронизация после review: top 5★ → select 4★, исключение с восстановлением исходного рейтинга, удаление только добавленных нами keywords, отсутствие receipt и ручная правка после записи. Проверить exclude → accept → undo и apply → undo → apply. Undo отменяет последнее доступное карточное действие только локально; внешний редактор меняется лишь при следующем apply с проверкой postimage.

## 12. Model и hardware compatibility

Для каждой заявленной связки host/model проверять реальную передачу изображений/кропов, стабильные IDs и структурированный результат, затем выполнять фото-evals. Отсутствие vision даёт degraded/unassessed, а не положительный художественный вывод. Model smoke установщика проверяет доступность, не заменяет закрытый quality suite.

[Ресурсная матрица](requirements.md) включает RAM, размер RAW, workers, cold/warm cache, место и совместную работу с редактором. Проверить деградацию при исчерпании места/памяти/сети, отсутствие загрузки тяжёлых ML-зависимостей по умолчанию, чистую установку production wheels и запись измеренных RAM/VRAM для каждого будущего local-vision профиля. Релиз не публикует экспериментальные ориентиры как измеренный минимум.
