# HTML-шаблон проверки отбора — следующая итерация

Статус: требования и контракт для будущей реализации. По указанию пользователя Tinder-подобный HTML-интерфейс не входит в первую итерацию. MVP выдаёт статический отчёт/contact sheets и готовую разметку; изменение решений пока доступно через агента и общий overrides-механизм.

## 1. Назначение и состав

Версионированный шаблон `resources/templates/review/`: HTML, CSS и JS, наполняемые результатами конкретной сессии. Основная карточка показывает фотографию, её место в серии, причину рекомендации, статус проверки и доступные альтернативы. Возможны обзор целиком, увеличение и кроп главного объекта.

Действия: **Принять**, **Отклонить из отбора**, **Пропустить**, **Отменить действие**, **Альтернативы**. Swipe вправо/влево дублирует принятие/отклонение; кнопки и клавиатура обеспечивают ту же функциональность. Настройка раскладки/доступности не должна менять смысл действий.

Принятие касается текущего набора — top или selects, указание набора всегда видно. Отклонение кандидата из top убирает его только из top, оставляя в selects при необходимости. Отклонение из selects убирает его и из top. Это `excluded_from_selection`, а не технический `status=reject`. Технический reject доступен отдельным явно обозначенным действием; удаление файла отсутствует.

```text
┌──────────────────────────────────────────────────────┐
│ Свадьба · Проверка TOP · 24 из 80      [Отменить]      │
│                                                      │
│                 Фотография                           │
│           [Целиком] [Увеличить / детали]               │
│                                                      │
│ Почему выбрана: выражение и момент                    │
│ Серия: 6 вариантов · есть 3 альтернативы               │
│                                                      │
│ [Отклонить из TOP]   [Пропустить]   [Принять в TOP]     │
│                                                      │
│ Альтернативы: [кадр B] [кадр C] [кадр D] [Сравнить]    │
└──────────────────────────────────────────────────────┘
```

Это схема требований, не готовый визуальный макет и не реализованный шаблон.

## 2. Поведение альтернатив

После отклонения показать ещё не отклонённые варианты той же серии в порядке ранее рассчитанного сравнения. У каждого варианта — причина предложения, отличие от предыдущего и возможность просмотра рядом. Выбранная альтернатива попадает в тот же набор, что исходный кандидат; старое решение сохраняется в истории.

Не возвращать отклонённый кадр при пересчёте. Технически непригодные/неоценённые варианты не выдавать за равноценные; сомнения видны. При отсутствии подходящих вариантов оставить место незаполненным и показать недостаток K/покрытия. Кандидат из другой группы предлагается только как явная замена сцены с проверкой брифа, не под видом альтернативного дубля.

Для composite-item карточка представляет комплект с подписью «нужна склейка» и списком required assets. Принятие/отклонение действует на логический пункт; свайп не выбрасывает отдельную экспозицию HDR или часть панорамы. Для RAW+JPEG показывается один пункт с доступом к связанным исходникам.

## 3. Контракт решений и сохранение

Будущая схема `ReviewAction`: action_id, session_id, base_revision, item_id, selection_scope=top|selects, action=accept|exclude|skip|replace|undo|mark_technical_reject, replacement_item_id при replace, undo_action_id при undo, timestamp. Backend проверяет membership, допустимость перехода и неизменность версии; повторный action_id идемпотентен.

Каждое действие формирует пользовательский override и новую revision. Undo — новое компенсирующее событие, не стирание истории. Отменяется последнее ещё не отменённое пользовательское действие в журнале сессии; `undo_action_id` должен указывать именно на него, произвольная отмена старых событий в этой итерации не поддерживается. Восстанавливаются прежние membership и overrides, включая блокировки альтернатив. После уже выполненного экспорта Undo меняет только локальную revision и показывает, что редактор требует синхронизации; повторное применение строит новый delivery-plan по предыдущему receipt. Экспорт не считается карточным действием в стеке Undo. Skip оставляет pending. Manual overrides блокируют автоматический возврат исключённых items. После replace пересчитать top⊆selects, K, coverage и protected sets; нарушенные ограничения показать человеку.

Предлагаемая реализация: локальная HTML-страница с session-scoped сервером на loopback и журналом на диске. Сам HTML не пишет произвольные локальные файлы и не вызывает MCP. Запросы записи проходят проверку Origin/session token/revision; endpoint читает только зарегистрированные previews данной сессии. Без CDN и внешних аналитических запросов; вывод текстов из EXIF/имён экранируется.

Изменение в браузере считается сохранённым после записи backend; при ошибке виден несохранённый статус. Reload, рестарт и повторное открытие восстанавливают прогресс. Две вкладки со старой revision получают конфликт, а не last-write-wins. Статический экспорт без сервера остаётся read-only и явно обозначается таким.

## 4. Применение разметки

HTML-review сохраняет решения локально. Команда **Применить разметку в выбранной программе** формирует новый delivery-plan на основании принятой revision и использует backend из конфигурации установщика. Receipt различает applied/skipped/failed и хранит ownership по полям; частичный сбой можно продолжить. Повторный план обновляет/снимает ранее записанные нами значения только при совпадении текущего значения с последним postimage, иначе сохраняет внешнюю правку и сообщает конфликт. Правило и baseline значений описаны в [distribution](../../distribution.md). Не переписывать внешний каталог при каждом свайпе.

В host-mediated режиме LightCraft/другого MCP интерфейс передаёт запрос агенту/адаптеру и показывает pending до фактического receipt. Наличие локальной веб-страницы не означает, что сервер сам получил доступ к инструментам Codex/Claude. Прямой transport, если будет реализован, проходит отдельную проверку.

Решения первой итерации совместимы с этим сценарием через SelectionItem IDs, overrides и revisions. Писать браузерный сервер и свайпы в первой итерации не требуется; достаточно не связать контракт результата с одним статическим представлением.

## 5. Приёмка во второй итерации

- Кнопки, клавиатура и свайпы дают одинаковые решения; есть zoom и сравнение вариантов.
- Отклонённый top-кандидат не получает технический reject; отклонение selects согласованно убирает top.
- Альтернатива не возвращает исключённый кадр и сохраняет комплект склейки.
- Accept/replace/undo/reload воспроизводятся из журнала; проверены exclude → accept → undo и apply → undo → apply; stale-tab и повтор события не портят состояние.
- Нет альтернативы → честный недобор; нет vision → нет выдуманных объяснений.
- Ошибка записи/экспорта видна, повтор безопасен; изменения в редакторе выполняются через выбранный backend.
- Измерить время проверки и ошибки пользователя против статического отчёта, провести keyboard-only проверку и тесты touch/desktop.

Сам шаблон входит только в release, где эта функциональность завершена и проверена. До этого production не содержит неработающих кнопок, скрытого прототипа и лишних UI-зависимостей.
